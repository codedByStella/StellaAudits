**AI-assisted, human-directed development.** StellaAudits is a Python-based website auditing and reporting application built to turn publicly accessible website signals into structured findings, a scored audit, and a client-ready report.

> **Portfolio publication — intentionally non-runnable.** This repository is a curated, redacted view of the project’s implementation and architecture. Proprietary checks, scoring logic, thresholds, and selected internal components have been withheld to protect the application’s intellectual property. The omissions are deliberate: this repository is intended for technical review, not as a hosted service, reusable audit product, or working copy of the application.

## Project overview

StellaAudits was designed as a local website-audit workflow for reviewing business websites individually or in batches. It combines static HTML analysis, optional browser-rendered measurements, historical comparisons, persistent lead tracking, and PDF report generation.

The original application produces a report containing:

- An overall Site Health score and letter grade.
- An executive summary.
- Findings organized by risk category, with explanations and recommended actions.
- A closing page with business contact information.
- A matching outreach draft for human review.

The repository includes sanitized representative reports generated by the application. They are genuine project outputs with identifying information redacted, not fabricated sample reports.

## Audit coverage

The original application organizes its checks into several areas:

- **Accessibility and legal risk** — static WCAG-oriented heuristics covering image alternatives, form labels, document language, heading structure, links, tables, and embedded frames. Checks requiring a rendered page are identified as requiring separate review rather than inferred from raw HTML.
- **SEO and visitor experience** — page titles, meta descriptions, headings, canonical links, viewport configuration, structured data, crawler directives, and sitemap discovery.
- **Security and liability signals** — a separate security-analysis pass. Implementation details are intentionally withheld from this publication.
- **Local SEO** — on-page business identity signals, LocalBusiness structured data, visible contact information, map embeds, and favicon detection.
- **Rendered-page analysis** — optional PageSpeed Insights integration for browser-measured performance and SEO data, with availability reported separately from the standard checks.
- **JavaScript-rendered content awareness** — detection of pages that appear to depend on client-side rendering, helping distinguish an unrendered HTML shell from a page with genuinely missing content.

These checks are preliminary automated signals. They are not represented as a certified accessibility assessment, penetration test, or legal determination.

## Application workflow

The original application supports two audit paths:

**Single-site audit**
1. Accept a website URL.
2. Retrieve and inspect publicly accessible page content and standard discovery resources.
3. Run the applicable audit modules.
4. Consolidate findings and calculate the report score.
5. Generate a PDF report and a corresponding outreach draft.
6. Store the result for later review.

**Batch audit**
- Accepts a list of URLs and processes them sequentially.
- Applies a delay between sites rather than treating a business list as a high-speed crawl.
- Records individual failures without intentionally abandoning the remaining batch.
- Reports progress and makes completed outputs available through the application.

The original workflow also maintains an audit history. When a domain is reviewed again, the application can compare its current findings with a prior successful audit and identify newly introduced, persisting, and resolved items.

## Architecture

The code is organized by responsibility rather than placing the entire workflow in a single application module.

| Component | Responsibility |
|---|---|
| `app.py` | Flask application and HTTP routes for the audit interface, batch workflow, and lead dashboard |
| `audit/fetcher.py` | Website retrieval and HTML parsing |
| `audit/accessibility.py` | Static accessibility heuristics |
| `audit/seo.py` | General SEO and discovery checks |
| `audit/local_seo.py` | Local-business and location-related signals |
| `audit/pagespeed.py` | Optional PageSpeed Insights integration |
| `audit/findings.py` | Shared finding representation and ordering |
| `audit/runner.py` | Audit orchestration |
| `audit/db.py` | SQLite persistence, audit history, and finding snapshots |
| `audit/outreach.py` | Human-reviewed outreach draft generation |
| `audit/report.py` | PDF report generation |
| `templates/` | Web interface and report presentation |

### Engineering considerations

A few implementation choices are central to the project:

- **Modular checks:** audit categories are separated so that individual passes can be developed and evaluated independently.
- **Shared finding model:** checks return a common finding structure, allowing the runner, scoring layer, report generator, and comparison workflow to work from consistent data.
- **Persistent history:** SQLite stores audit records and compact finding snapshots for later comparison.
- **Optional external analysis:** PageSpeed Insights is an additional pass rather than a dependency for the standard HTML-based checks.
- **Human-reviewed outreach:** the application generates drafts only; it does not automatically send messages.
- **Conservative reporting:** checks that cannot be established from the available page content are identified as limitations or manual-review items rather than presented as verified results.

## AI-assisted development methodology

StellaAudits was developed through an iterative, AI-assisted process. AI is disclosed as part of the development methodology, not hidden or presented as unaided authorship.

Models were used to accelerate implementation, explore alternatives, and investigate unfamiliar problems. Their output was not treated as authoritative. The engineering value comes from how the tools are directed, challenged, and held accountable to the wider application context.

### 1. Challenge the reasoning

Proposed implementations are interrogated rather than accepted at face value. Their assumptions are questioned, and design decisions are expected to have a defensible rationale. Models are allowed to explore beyond the immediate task when a detour may expose a useful conflict, application, or overlooked use case, provided the reasoning holds up. Agreement is not the objective; finding the strongest defensible solution is.

### 2. Account for failure modes

Context-window limits, conversational drift, hallucinations, and stateless API calls all affect reliability. Weak information sources and search systems that reward visibility rather than accuracy introduce further risks. A confident answer can still be wrong, incomplete, or detached from the actual implementation. Those limitations must be accounted for rather than mistaking fluency for evidence.

### 3. Verify, don't defer

Models can reframe a question, narrowly rebut a claim while missing its substance, distort emphasis, construct strawmen, or dismiss inconvenient evidence. Discussions are brought back to their original context, and disagreements are investigated rather than resolved by automatically accepting either the model's conclusion or the developer's own. Model reasoning is adopted only when it withstands scrutiny.

**The principle:** AI can generate possibilities, challenge assumptions, and accelerate execution. It cannot be trusted to police its own reasoning. That responsibility stays with the operator, who must preserve context, demand intellectual honesty, and verify that an answer has merit before building on it.

AI assistance is therefore treated as a development tool, not a substitute for engineering judgment. Responsibility for requirements, architecture, integration, review, verification, and final implementation decisions remains with the developer.

## Publication scope

## Limitations

StellaAudits is an automated preliminary review tool. Static HTML inspection cannot establish every issue that depends on browser rendering, interaction, assistive technology, or server-side behavior. PageSpeed results are available only when the optional integration is configured in the original application. Findings require human verification before being used for compliance, legal, security, or contractual decisions.
